## 2. Critical issues (evidence-based only)

1. **`/odom` drift under wheel-slip corrupts any map built naively from it.** Measured directly this project: over 0.35 m of drift in under 15 s during a recovery maneuver, once even reporting forward progress while the vehicle had genuinely moved backward. This is not a Member 1 defect (dead-reckoning odometry behaves this way by definition) but it is a hard constraint every future perception/mapping member must design around from day one, not discover late.
2. **Host rendering performance degrades severely over long sessions.** Observed directly: GUI-attached RTF fell to 0.002-0.006 (0.2-0.6%) after several hours of continuous use in this session, with `gz sim gui` measured at 734% CPU, while a fresh headless run measured RTF ≈ 0.42 immediately after. This is a WSLg/host environment issue, not a code defect, but it materially affects how testing (especially long autonomous runs) should be structured — headless where possible, and sessions should not be assumed to stay performant indefinitely.
3. **`goal_navigator.py` is dead code.** Subscribes to `/ground_truth_pose`, a topic removed from `config/bridge.yaml` when an earlier plugin experiment was reverted. Not part of Member 1's scope to fix, but should not be mistaken for working functionality by a future member.

## 3. Future risks (not yet observed — reasoned from the architecture, not invented without basis)

Priority reflects likely impact on whether the final system works, not certainty that the risk will materialize.

- **P0 — Perception/mapping repeating the odometry-drift feedback loop.** Member 4's prototype hit a real, measured version of this (drift → phantom obstacles → spurious recovery → more slip → more drift) and fixed it by suspending map updates during recovery maneuvers specifically. Member 2's real terrain engine will face the identical root cause (dead-reckoning-only pose) and needs an equivalent mitigation from the start, not as a late patch.
- **P1 — Coordinate-frame assumption mismatch.** Member 1/4 currently assume `odom`-only (no `map` frame, no localization). If Member 2 introduces any drift-correcting estimator (`/state/estimated`) that implies a `map` frame, every consumer's frame assumptions need to be revisited together, not per-member.
- **P1 — Computational load stacking.** Stereo depth + semantic inference + Hybrid A*/DWA + CBF, concurrently, on a host already shown to strain under Gazebo rendering alone. Should be profiled incrementally as each member is added, not assumed to fit.
- **P2 — Hybrid A* motion-primitive discretization producing false "no path" results in tight spaces.** Observed once this project (a fixed-arc primitive size was too coarse to find a valid escape from a tight rock gap the vehicle could physically clear at finer motion resolution; fixed by reducing the primitive step size). Not confirmed as a general problem, but the failure mode is real and worth testing for again once Member 2 supplies denser/more accurate terrain data.
- **P2 — CBF command conflicts with DWA's own feasibility constraints.** Two independently-reasoning safety/feasibility layers (DWA's dynamic window, Member 5's CBF) filtering the same command stream could disagree in ways neither alone would produce — untested, architecture-level concern only.
- **P2 — Costmap resolution/representation mismatch.** Member 4's prototype currently assumes a 0.2 m grid; Member 2's final terrain representation may differ (e.g., a true 2.5D elevation grid at a different resolution). Needs reconciling when Member 2 lands, not assumed compatible.
- **P3 — Sensor synchronization.** Stereo + LiDAR + IMU timestamps have never been exercised by an actual fusion algorithm in this project (Member 4's prototype uses LiDAR + odom only). Low priority only because no fusion work exists yet to expose the problem.
- **P3 — Repeat of the C++/Python build-system boundary if more nodes migrate later without following this pass's pattern.** Low risk because the pattern established here (hybrid `ament_cmake`+`ament_cmake_python`, wrapper scripts for `ros2 run` entry points) is documented and works; risk is only in a future contributor not reusing it.

## 4. Do-not-overengineer check

No custom message types, middleware, databases, or microservices were introduced by this audit — the architecture recommended in `INTERFACE_COMPATIBILITY_MATRIX.md` proposes standard ROS 2 message types everywhere a standard type plausibly suffices, and only flags three genuinely open type decisions for future members to settle themselves. The C++ migration (`CPP_MIGRATION_REPORT.md`) touched exactly one file — no framework was introduced, no unnecessary abstraction layer was added around it. The build-system change (ament_python → ament_cmake) was the minimum necessary to host a real C++ executable alongside the existing Python package, not a larger restructuring.

## 5. Recommended implementation order

Not the original 2→3→4→5→6 numbering — based on actual dependencies and what already exists in this codebase:

1. **Member 2 (perception + terrain engine) first.** It is the foundational data layer every other future member needs (`/terrain/costmap`, `/state/estimated`), and Member 4's prototype already demonstrates, concretely, what a simplified version of Member 2's job looks like when built directly against Member 1 — that prototype is a usable reference, not a blocker.
2. **Bring Member 6 (viz/metrics) in incrementally alongside Member 2, not last.** Being able to *see* Member 2's costmap/elevation/entropy output live (RViz) will materially speed up Member 2's own debugging — the same reason this project's Member 4 work relied heavily on published `/planner/global_path`/`/planner/local_trajectory` for visualization during its own development.
3. **Integrate Member 4's final version** by repointing its costmap/terrain-cost consumption from its own internal `costmap.py` to Member 2's published topics, and renaming its output from `/cmd_vel` to `/planner/proposed_cmd_vel`. This is an integration task on top of an already-working prototype, not a from-scratch build.
4. **Member 3 (semantic) after Member 2/4 are integrated**, since it is explicitly optional and entropy-gated by design — a refinement to planning cost, not a hard dependency for a functioning autonomous loop.
5. **Member 5 (CBF safety) last.** It depends on Member 4's final proposed-command output being stable, and per this audit's own caution, a safety filter deserves the most validation time of any component before being trusted — rushing it earlier than the rest of the stack is stable would be the wrong tradeoff.
